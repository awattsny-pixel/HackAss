# HashCanon-1 (`HACKASS-CANON-1`) — the canonical text and hash of a hack version

Implemented twice and checked against each other: SQL `app_content.canonical_text_json(jsonb)` (the database is authoritative,
`supabase/migrations/20261014090100_f2b_canonical_hash.sql`) and TypeScript `canonicalText()` in
`src/modules/submissions/hashcanon.ts`. Shared golden vectors: `tests/fixtures/hashcanon-vectors.json` (46), generated by
`scripts/gen-hashcanon.mjs` from the TypeScript implementation and checked against SQL independently by
`supabase/tests/database/030_hashcanon_vectors.test.sql` (canonical text, SHA-256, and — for 34 vectors — the same text after the
document is stored in the real tables). Ten further vectors are **rejection** vectors: identifiers in a non-canonical spelling, which SQL, TypeScript and storage must all refuse. Three canonical texts are also written out by hand in `tests/hashcanon.test.ts`.

## What is hashed (and what is not)
**Hashed:** exactly the author-written content below. **Not hashed:** `hacks` identity and slug, `version_no`, `created_by`,
timestamps, the seal columns (`frozen_at`, `content_hash`, `canon_version`), `version_lifecycle`, `submissions`, and every future
staff/system record about a version (risk class, rights reviews, decisions). None of those can be supplied through `save_draft`.

## The document
```
{ category_slug, title, summary, outcome, difficulty, time_min_minutes, time_max_minutes, cost_min_cents, cost_max_cents,
  currency, estimate_basis, ai_requirement, limitations,
  steps: [string], materials: [{name, detail?}], requirements: [{kind, name, detail?}], tags: [string],
  attributions: [{role, profile_id?, external_name?, external_url?}],
  source_claims: [{kind, canonical_url?, source_author?, license_spdx?, license_version?, permission_note?, asset_rights_note?}],
  assets: [{asset_id, sha256}] }
```
Absent and `null` mean the same thing. An absent list is an empty list. In the database `category_slug` is resolved through
`categories`, and the document is rebuilt from the committed rows by `app_content.version_doc(version_id)`.

## Normalization (applied to every string, on write and again when hashing; idempotent)
1. CRLF becomes LF, then a lone CR becomes LF.
2. Unicode NFC (`normalize(..., 'NFC')` in PostgreSQL, `String.prototype.normalize('NFC')` in TypeScript).
3. Nothing else: no trimming, no case folding. Whitespace and case are significant.
The database refuses control characters other than LF (and C1 controls) in stored text, and bounds every length.
**Unicode version:** PostgreSQL 17 here uses Unicode 15.1; Node 22 uses 15.1 and Node 24 uses 16. The vectors stay inside 15.1;
characters added or re-normalized after 15.1 could differ between the two implementations and are not covered.

## Identifiers (strict: not normalized, REJECTED)
`profile_id` and `asset_id` must already be **lowercase, hyphenated UUIDs** (`8-4-4-4-12` lowercase hex digits) and `sha256` must be **64 lowercase hex characters**.
Anything else — uppercase, braces, a `urn:uuid:` prefix, missing or oddly placed hyphens, a short or non-hex digest — is an error
(`PT422 invalid_content`, detail = the field name; TypeScript throws `CanonError` with the same field name) in the canonical function, in
`save_draft`/`write_doc`, and in TypeScript. PostgreSQL would otherwise accept several of those spellings when casting to `uuid` and rebuild the
document with its own canonical spelling, so the text hashed from the input could differ from the text hashed from the stored rows. Rejecting at input
removes that class of disagreement. `category_slug` is resolved through `categories`, whose slugs are **immutable** (names are editable).

## Integers
ASCII decimal, no sign, no leading zeros, at most 15 digits (below 2^53). Floats, exponents, negative numbers, strings and booleans are
errors. (A JSON document that spells an integer `5.0` is rejected by the database; a JavaScript value cannot distinguish `5.0` from `5`.)
Money is cents, time is minutes.

## The text
`HACKASS-CANON-1\n`, then these lines, in this order. **`<v>` is `<utf8 byte length>:<value>`, or `-:` when the value is absent.** Because every value is
length-prefixed, no value can forge a field boundary (the vectors include injection attempts).

| Part | Line format |
|---|---|
| scalars, in order: `category_slug`, `title`, `summary`, `outcome`, `difficulty` | `name:<v>\n` |
| integers, in order: `time_min_minutes`, `time_max_minutes`, `cost_min_cents`, `cost_max_cents` | `name:<v>\n` |
| scalars, in order: `currency`, `estimate_basis`, `ai_requirement`, `limitations` | `name:<v>\n` |
| steps (array order, position = index + 1) | `steps:<count>\n` then `step;<position>;<v body>\n` each |
| materials (array order) | `materials:<count>\n` then `material;<position>;<v name>;<v detail>\n` |
| requirements (sorted by kind, then name, as UTF-8 bytes) | `requirements:<count>\n` then `requirement;<v kind>;<v name>;<v detail>\n` |
| tags (sorted by slug, UTF-8 bytes) | `tags:<count>\n` then `tag;<v slug>\n` |
| attributions (array order = attribution number) | `attributions:<count>\n` then `attribution;<n>;<v role>;<v profile_id>;<v external_name>;<v external_url>\n` |
| source claims (array order = claim number) | `source_claims:<count>\n` then `claim;<n>;<v kind>;<v canonical_url>;<v source_author>;<v license_spdx>;<v license_version>;<v permission_note>;<v asset_rights_note>\n` |
| assets (sorted by lowercase SHA-256 hex, UTF-8 bytes) | `assets:<count>\n` then `asset;<v sha256 hex>;<v asset_id>\n` |

Sorting compares the UTF-8 bytes of the normalized strings (`bytea` order in SQL, byte-wise comparison in TypeScript). `profile_id`,
`asset_id` are lowercase hyphenated UUID text; `sha256` is 64 lowercase hex characters.

## The hash
`SHA-256` over the UTF-8 bytes of the text, stored as `bytea` in `hack_versions.content_hash`; `canon_version` = 1. The database computes it
(`app_content.version_hash`) from committed rows; the freeze trigger recomputes it and refuses any stored value that differs.
