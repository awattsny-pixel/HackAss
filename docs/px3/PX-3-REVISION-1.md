# PX-3 revision 1: focused delta for PX-3a approval

Responds to the owner's review of 2026-10-20. **Nothing is a migration; nothing was applied.** The revised draft SQL was compiled and rehearsed in a rolled-back transaction on the disposable local database (**55 checks pass**; afterwards the tables and the helper schema did not exist).

| # | Review point | Change |
|---|---|---|
| 1 | Preserve what was actually tried | `api.save_reflection` now **requires** `p_expected_prompt_version` and refuses a different current version (PT409 `version_conflict`). `saved_reflections` gained snapshot columns `starting_prompt`, `prompt_title`, `origin_kind`, `origin_slug`, `origin_title` (with the existing `attempted_prompt`, `prompt_version`), copied by the database at save time and never updated. `get_my_result` and `list_my_results` read only these snapshots (no join to the mutable parent). Rehearsed: parent edited to v3 and renamed, result still shows the v2 text, the old starting prompt, the old title. |
| 2 | "Save prompt and result" as one transaction | new `api.save_prompt_and_result(request, prompt_doc, result_doc, id?, expected_version?)`: validates both documents first, then writes the prompt (create or versioned update) and the result in one function = one transaction. Rehearsed: invalid result writes nothing; the result quota tripping **after** the prompt update rolls the prompt update back (title and version unchanged). |
| 3 | Newer edits stay dirty while saving | specified in the plan (section 3): a monotonic draft revision; a Save captures its revision; success marks only that revision saved; newer typing shows "Changed since last save" and keeps the leave-page warning; failures change nothing; out-of-order responses ignored; one save in flight; lost-response conflicts resolved by comparing the fetched content. Regression tests are listed in the PX-3c acceptance (delayed-response reducer tests). No SQL. |
| 4 | Bind create retries to their payload | `request_hash` (SHA-256 of the canonical payload; for results it also covers the parent prompt id and expected version) stored on both tables. Identical retry: the stored row is returned (for the combined update, even after the prompt moved on). Same request id with different content, parent or version: PT409 `request_reuse`. Rehearsed in six ways. |
| 5 | Privacy wording | provisional text is now "Private to your account; not shared with other members. Please don't store passwords or other secrets in prompts."; "only you can see it" and "no human access" removed; the final notice must state that privileged database operators and backups are outside these restrictions. |
| 6 | Complete the undrafted functions | `update_my_reflection`, `delete_my_reflection` (version-checked, snapshots untouched) and `export_my_data(kind, after_id?, limit?)` (kinds `summary`/`prompts`/`results`, at most 50 rows per call, own rows only, no owner id or request hash). `get_my_prompt` also returns `result_count` and `delete_my_prompt` returns `results_deleted` so the confirmation can state the cascade. |
| 7 | Decisions recorded | quotas 100 / 50 / 500, hard delete with cascade warning, no staff access, bounded export, module `mywork`, demo origin allowed, output formats in the module, privacy wording provisional (plan section 10). |
