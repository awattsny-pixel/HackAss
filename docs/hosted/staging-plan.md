# Staging plan: a fresh, isolated `hackass-staging` Supabase project

Prepared from local files only; nothing here has been created or contacted. Items marked **OWNER** need an owner decision, credential or account action. Items marked **CONFIRM** are written from general knowledge of the Supabase platform and must be checked in the dashboard when the project exists.

## 1. Isolation requirements

* A **new** Supabase project, created for this purpose, named `hackass-staging`. It must not be the project whose keys appear in git history (see `credential-retirement.md`) and must not share a database, Auth user table, storage or keys with it.
* **Synthetic data only.** Every user, hack and publication created is generated by the verification procedure, with email addresses on the reserved `example.test` domain and a run label in the content. No real person's data, no copy of any other database.
* **No application deployment points at it.** No hosting-provider environment variable (preview or production) is set to the staging URL or keys. Staging is exercised only by the verification scripts run from an operator machine.
* Treat the project as **disposable**: it is deleted (or at least paused) when the verification is accepted.

### Hosted-specific risks the first apply will reveal (unknown until run)

These are the points where hosted Supabase may differ from the local stack. A failure at any of them is a result to report, not something to patch by hand on the hosted database:

* **Role creation and membership.** Migration 1 creates `hackass_owner` and `hackass_worker` and runs `grant hackass_owner to postgres with inherit false, set true`. It requires the hosted `postgres` role to hold `CREATEROLE`-style rights and the ability to grant membership.
* **Triggers on `auth.users`.** Migration 2 creates `hackass_account_created` and `hackass_account_deleted` on `auth.users` as `postgres`. The design notes say "postgres owns the right to add triggers to `auth.users`" locally; hosted feasibility is unverified (spike S3 / F2-A note).
* **The session bridge.** `app_bridge.session_valid` is a `postgres`-owned function reading `auth.sessions` (migration 3). It depends on the hosted `postgres` role keeping read access to `auth.sessions` and `USAGE` on schema `auth`.
* **Extensions.** The migrations create none; `pgcrypto`, `citext` and `pg_trgm` must already be available (`000_platform.test.sql` asserts them locally).
* **Role defaults.** `alter role ... set` defaults (statement timeout, search path) must be persisted and honored through the pooler.

## 5. Worker connection method

* The worker login is `hackass_worker` (`LOGIN`, `NOINHERIT`, connection limit 10, no table privileges, `EXECUTE` on the `worker.*` functions only). **It is created without a password** (`20261013130000...`); the operator sets one out of band.
* **Password setup (OWNER, one time, after migration 1 exists):** generate at least 32 random characters; set it with a `postgres` session so the password never appears in shell history: read it from standard input or a prompt (`\password hackass_worker` in `psql` against the pooler or direct connection) and store it in the password manager. It is never written to the repository, an issue, a log, or a command line.
* **Connection path under test: the hosted pooler (Supavisor), not the direct host.**
  * username form: `hackass_worker.<project-ref>` (CONFIRM the exact form in the project's Connect panel);
  * **transaction mode** (port 6543 in the usual configuration) is the mode named by spike S5 and is tested first;
  * **session mode** (port 5432 on the pooler host) is tested as well, because transaction mode does not preserve session-level `SET`;
  * both with SSL; hostnames are read from the dashboard at execution time and never committed.
* **What must hold** (checks H9 and H10): password authentication succeeds; a wrong password is refused; `worker.healthcheck()` works; the role can read no table, cannot `SET ROLE`, cannot execute any `api.*`, `app_*` or `app_budget.*` function; the role defaults (`statement_timeout 30s`, `idle_in_transaction_session_timeout 30s`, `search_path ''`) are visible through the pooler; and the job functions work in transaction mode (`claim_job` uses `FOR UPDATE SKIP LOCKED` and per-call locking only, with no session state).
* The direct database host is not used for the worker (it is IPv6-only on some plans); the migration step uses the `postgres` login, and the pooler's session-mode port can serve that if the direct host is not reachable (CONFIRM).

## 7. Evidence handling

* Outputs are written to a local directory outside the repository during the run, then **redacted** (tokens, keys, passwords, connection strings, email addresses other than the synthetic ones, JWT bodies) and only the redacted copy is brought into the repository, in a separate reviewed commit.
* Recorded facts that are allowed: the project reference, region, platform and Postgres versions, extension versions, key model, token algorithm and lifetime, check results with exit statuses, timings, HTTP statuses and error codes.

## 8. Explicitly out of scope for this staging run

* Browser behaviour over HTTPS (spike S1), because there is no browser application to test.
* Email delivery and the email-confirmation flow (built-in sender restrictions); the local equivalent L1 remains the only evidence.
* Load or performance measurement (that belongs to M-DISCOVERY).
* Any deployment, any application hosted anywhere, any real user.

## 9. Cost and cleanup (estimates; CONFIRM against the owner's plan and current pricing)

* **Supabase:** a free-plan project costs nothing but the plan limits the number of active free projects per organization and pauses inactive projects. If a paid plan is needed, expect a monthly base fee plus compute; a few days of use is a small fraction of one month but billing granularity and minimums are the owner's to check. I have not verified current prices.
* **GitHub Actions:** the first push triggers the workflow reviewed in `ci-review.md` (three jobs, about 25 to 35 minutes of Linux runner time in total, estimated from local timings); free for public repositories, within the monthly free minutes for private ones on typical plans (CONFIRM).
* **Cleanup responsibilities:**
  * Owner: delete (or pause then delete) the `hackass-staging` project; revoke any key or token created for the run; delete the temporary remote branch; remove any repository secret that was set (none is planned); clear shell sessions holding exported secrets.
  * Operator machine (me, under authorization): remove local environment files and evidence working directories outside the repository after redaction; never commit them.
  * Synthetic content cannot be deleted row by row by design (publications, decisions and ledgers are append-only and the Auth user deletion marks accounts `deleted` rather than removing them). Deleting the project is the cleanup.
