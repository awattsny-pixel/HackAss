# PX-2b: Auth handlers, sessions and email-link flows (implemented locally; results of the local integration checks)

Branch `px2b-auth` (built on the baseline `c423aa4` plus the uncommitted UX-08 v2 and PX-2a work, reconciled before building). **Uncommitted. Local only: no hosted contact, no migration, no deployment.** PX-2c screens are held: the pages below are unstyled scaffolding to exercise the flows.

## 1. What was built
| Route | Purpose |
|---|---|
| `GET /auth/callback` | read-only page for an emailed link (invite, recovery, email change). Never calls the provider, sets no cookie, does not consume the token |
| `POST /auth/callback/exchange` | the one-time exchange (same-origin, throttled first); starts the session; 303 to set-password for invite/recovery; sets the setup marker |
| `GET/POST /auth/set-password` | choose a password: T2 session, same-origin, throttled, validated (12 characters to 72 bytes), clears the marker, 303 to a validated `next` |
| `POST /auth/sign-in` | email + password; throttled; identical failure for every cause |
| `POST /auth/sign-out` | revokes this device's session at the provider; always expires the cookies |
| `POST /auth/recovery/request` | always 202 with one sentence; per-address and per-email limits |
| `GET /auth/session` | the **provisional** signed-in indicator (T1) and the place an expired token is refreshed |
| `GET /auth/session/verified` | stand-in for any private read or write (T2, and the setup nudge); replaced by real operations in PX-3 |

Composition root: `app/auth/_server/` (`kit.ts`, `pages.ts`). The identity module gained `provider.ts` (translation of Auth-client results; only explicit credential verdicts are 401, everything uninterpretable is a retryable 503) and `setup-marker.ts`. Platform additions: `createBoundedFetch` (every Auth call bounded: 3 s each, 5 s per request, including signing-key retrieval), optional `fetch` on `createUserDb`/`createPublicDb`, a cap on the session cookie lifetime, and the optional variables `AUTH_THROTTLE_SECRET`, `AUTH_SETUP_MARKER_SECRET` (at least 32 characters) and `TRUSTED_CLIENT_IP_HEADER` or `TRUSTED_PROXY_HOPS`. Without the two secrets the handlers answer 503 (fail closed).

**The setup marker is a UX consistency rule, not an authorization boundary.** It expires after 15 minutes and removing the cookie lifts it; nothing about access or data protection depends on it (check P4 demonstrates the bypass on purpose).

## 2. Local pilot Auth stack (`supabase-pilot/`, `scripts/px2b-pilot.mjs`)
A separate local project (`hackass-px2`, own ports) so the F2 stack and its tests are untouched. Differences from `supabase/config.toml`: public sign-up disabled, minimum password 12, site URL `http://localhost:3100`, email templates (invite, recovery, email change) linking to `{{ .SiteURL }}/auth/callback?type=...&token_hash={{ .TokenHash }}`, the local email-send limit raised (50/hour; the default 2/hour makes tests impossible), unused services off. The hosted project is not changed by any of this; the same settings must be applied there as a separate, owner-authorized step.

Run: `node scripts/px2b-pilot.mjs up`, `npx next build`, `npm run px2b:local` (the script starts the app itself with throwaway secrets, puts a fault-injecting proxy in front of Auth, and uses the local stack's service key only to invite and delete test users).

## 3. Provider facts verified against the installed local provider (not assumed)
* Public sign-up: refused by the provider, HTTP 422 `signup_disabled`.
* Password length: 11 characters refused (`weak_password`), 12 accepted; **72 bytes accepted, 73 bytes refused** (`validation_failed`), multi-byte counted in bytes (36 two-byte characters accepted, 37 refused); a password is never silently truncated (the full password signs in). The module's 12-character minimum and 72-byte maximum therefore match the provider and are enforced.
* Access tokens are ES256 (verified through the signing keys, not a shared secret).
* Concurrent refresh: 8 simultaneous requests carrying the same expired session all succeeded and all issued rotated cookies (8 provider refresh calls; **no single-flight in the app**). After the provider's 10-second reuse interval, the cookies from the first, middle and last response of such a race could all still refresh and pass T2: the race did not revoke the session family.
* The provider rate-limits recovery emails per user on its own (a second request within about a minute for the same member is refused), independently of the application's limits.
* The Auth library itself prints an error object (name, message, `code`) to the server output when a revoked session's refresh is attempted (for example `refresh_token_not_found`). It contains no token or address; the log check below looks for token values, not for that code.

## 4. Results (`npm run px2b:local`, 34 checks after revision 2)
See `px2b-local-results.txt` (attached to the review package). Summary of what is demonstrated:
* **Registration refusal (R1, R2):** provider-level refusal; no sign-up route; `signup`/`magiclink` links refused; legacy sign-up API still 503.
* **Callback (I1 to I5):** GET is read-only and repeatable; same-origin enforced (missing, foreign, `null` and other-port origins refused); exchange succeeds once; **replay refused**; malformed, unsupported and provider-error links; hostile `next` values fall back to `/spark`.
* **Cookie flags (I3):** session cookies `HttpOnly`, `SameSite=Lax`, `Path=/`, Max-Age 604800 (the library's 400-day default is capped); marker cookie `HttpOnly`, 900 s. `Secure` is not set locally (plain HTTP); `createUserDb` sets it for staging and production. **Real HTTPS verification of the flags is still outstanding.**
* **Password setup (P1 to P4):** private operations refused until a password is set; weak, too long, control-character, no-session, cross-origin and oversized requests refused; success clears the marker; **the documented bypass** (cookie removal, tampered marker) works as intended for a UX rule.
* **Sign-in and throttling (S1 to S3):** identical 401 for wrong password and unknown address, no cookie on failure; the 6th attempt is 429 with Retry-After **and never reaches the provider**; cross-origin and origin-less POSTs refused on all five mutating endpoints.
* **Refresh and sign-out (F1 to F4):** expired token refreshed with rotated cookies; concurrent refresh safe (section 3); after sign-out the **old cookie still passes the provisional T1 indicator (documented limitation) but is refused at T2 and cannot be refreshed**.
* **Recovery (V1, V2):** identical 202 for a member and an unknown address, mail only to the member, per-email limit stops email bombing; the link is not consumed by GET, consumed once by the exchange, the old password stops working, replay refused.
* **Provider limits (W1):** section 3.
* **Outages (O1 to O4):** with Auth down, a refresh gives a retryable 503 **with no Set-Cookie** (the session is not cleared) and no redirect; T2 gives 503 and never a downgrade; T1 with a valid token and cached keys keeps working; sign-in and the callback exchange give 503 and **the one-time link still works afterwards**; with Auth hanging, a cold signing-key retrieval and a T2 check each return 503 in about 3.0 s; **in a real browser the member's unsaved draft, the page and the document survive a failed verification** (no navigation, no unload, no dialog).
* **Logs (L1):** no password, token value, link parameter, cookie value or email address in the app's output; events are logged by name with a kind only.

## 5a. Four fixes after review (revision 2)
1. **Recovery cooldown no longer reveals membership.** The provider's own per-user cooldown (about a minute) applies only to addresses that belong to a member. The recovery handler now answers every provider outcome except an outage with the same 202 (status, body and headers identical to an unknown address; check X1 compares a member's immediate repeat with two unknown-address requests). Existence-independent answers remain: our throttle (429 with Retry-After) and an outage (503). Consequence: a member who repeats the request inside the cooldown simply gets no second mail.
2. **An emailed link never switches accounts silently.** With a session cookie present, the link page says so ("You are signed in on this browser... may be for a different person") and its button reads "Sign out and continue"; the exchange without the explicit `confirm_switch` is refused (409), consumes nothing and leaves the session untouched; with confirmation the current session is ended at the provider **first** (if that cannot be done because Auth is unavailable, the handler stops with 503 before the one-time token is consumed), then the link is exchanged (checks X2 for an invitation link, X2b for a recovery link, X3). The cookie check on GET uses no network call.
3. **Body limit enforced while streaming, with a deadline.** `readBodyBounded` (`src/platform/http/body.ts`) counts bytes as they arrive and cancels the read as soon as the 8 KiB limit is passed; a declared Content-Length above the limit is refused without reading; the whole read has a 3 s deadline (408); unsupported content types are 415 before any read; invalid UTF-8, malformed JSON and a failing stream are 400; a 413 or 408 response carries `Connection: close` so the rest of an oversize upload is not read. **Stated precisely:** the check is per chunk the platform delivers, so the server can consume up to one delivered chunk (Node delivers up to 64 KiB, which matches the 65,536 bytes a reviewer observed) beyond the limit before refusing; consumption is bounded by one chunk, no longer by the whole body. The local run (B1) shows a 4 MiB chunked upload without Content-Length answered 413 in about 5 ms (the figure of how much the client managed to write is limited by socket buffers and is not a measure of what the server read); a stalled upload and a 1-byte-per-200-ms drip each got 408 at about 3.0 to 3.2 s; nothing reached the provider. A tighter bound than one platform chunk is not possible at this layer.
4. **Unknown or unavailable provider failures are retryable 503, never revocation.** **Availability takes precedence:** a network failure, timeout, rate limit or any 5xx is unavailable whatever name or code the error carries (an `AuthSessionMissingError` or `AuthInvalidJwtError` arriving with a 503 is an outage). Only then do explicit verdicts count as revocation: a session-missing error, an invalid-JWT error, or a known code (`session_not_found`, `session_expired`, `bad_jwt`, `invalid_jwt`, `refresh_token_not_found`, `refresh_token_already_used`, `user_not_found`, `user_banned`). Any other code, a missing code, or any other 4xx (including 401/403 without a known code) is "unavailable". The callback exchange shows "expired" only for an explicit expired/used-link verdict; everything else is 503. Check U1 injects an unknown HTTP 400 into the user check, the refresh, sign-in and the link exchange: each answers 503 (T2 never 401, refresh sets no cookie, sign-in is not read as wrong credentials, the link is not shown as expired), and the same session, refresh and link work afterwards.
